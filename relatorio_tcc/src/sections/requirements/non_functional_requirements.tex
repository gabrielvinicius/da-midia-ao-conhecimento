\subsection{Requisitos Não-Funcionais}
\label{sec:requisitos_nao_funcionais}

Os requisitos não-funcionais definem os atributos de qualidade e as restrições sob as quais o sistema deve operar. Eles são cruciais para guiar as decisões arquiteturais do projeto.

\begin{description}
    \item [RNF1 - Extensibilidade] O sistema deve ser projetado para permitir a fácil adição de novos tipos de mídia, novos provedores de serviços (e.g., outros modelos de IA) e novas etapas no pipeline de processamento, com o mínimo de modificação no código existente. Este requisito justifica a adoção de uma \textbf{arquitetura de plugins orientada a eventos} e o uso dos padrões \textit{Strategy} e \textit{Factory}.

    \item [RNF2 - Manutenibilidade e Baixo Acoplamento] A arquitetura deve promover um baixo acoplamento entre os diferentes módulos de negócio (Bounded Contexts). A modificação de um módulo, como o de sumarização, não deve impactar diretamente o módulo de transcrição. Este requisito é o principal motivador para a adoção dos padrões \textbf{CQRS} e de uma \textbf{Raiz de Composição explícita} para a injeção de dependências.

    \item [RNF3 - Resiliência] O sistema deve ser resiliente a falhas em serviços externos dos quais depende, como as APIs de modelos de IA. Uma indisponibilidade temporária em um provedor de sumarização não deve causar falhas em cascata ou esgotar os recursos do sistema. Este requisito é diretamente atendido pela implementação do padrão \textbf{Circuit Breaker}.

    \item [RNF4 - Observabilidade] Dado o caráter distribuído e assíncrono do sistema, deve ser possível rastrear o fluxo completo de uma requisição, desde o upload da mídia até a conclusão do processamento, e monitorar a saúde e a performance de cada componente. Este requisito justifica a implementação dos três pilares da observabilidade: \textbf{logs estruturados}, \textbf{métricas Prometheus} e \textbf{tracing distribuído} com OpenTelemetry.

    \item [RNF5 - Performance e Responsividade] A API deve permanecer responsiva e com baixa latência, mesmo durante o processamento de mídias grandes e demoradas. As operações de longa duração não devem bloquear as requisições do usuário. Este requisito é atendido pela adoção de uma \textbf{arquitetura totalmente assíncrona}, utilizando Celery e Redis para executar todas as tarefas de processamento em segundo plano.

    \item [RNF6 - Segurança] O acesso aos dados e às funcionalidades do sistema deve ser restrito a usuários autenticados e autorizados. As senhas dos usuários devem ser armazenadas de forma segura, e a comunicação deve ser protegida. Este requisito é atendido pela implementação de autenticação baseada em tokens \textbf{JWT (JSON Web Tokens)} e pela aplicação de verificações de autorização em todos os endpoints da API.
\end{description}

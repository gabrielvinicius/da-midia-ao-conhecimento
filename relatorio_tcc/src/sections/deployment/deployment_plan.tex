\subsection{Plano de Implantação}
\label{sec:plano_implantacao}

A estratégia de implantação da plataforma foi projetada para ser robusta, segura e otimizada para um ambiente de produção, utilizando containers Docker e Docker Compose para a orquestração dos serviços. Esta abordagem garante a portabilidade e a consistência do ambiente, desde o desenvolvimento até a produção.

\subsubsection{Estratégia de Containerização (Dockerfile.prod)}

Para a criação das imagens da aplicação, foi adotada uma abordagem de \textbf{multi-stage build} no arquivo \texttt{Dockerfile.prod}. Esta técnica otimiza o tamanho da imagem final e aumenta a segurança, separando o ambiente de compilação do ambiente de execução.

\begin{itemize}
    \item \textbf{Estágio de Build (builder)}: Um primeiro estágio utiliza uma imagem Python completa (e.g., \texttt{python:3.11}) que contém as ferramentas de compilação necessárias para instalar as dependências do projeto a partir do arquivo \texttt{requirements.txt}. As dependências são instaladas como \textit{wheels} em um diretório temporário, aproveitando o cache de camadas do Docker para acelerar builds futuros.
    
    \item \textbf{Estágio Final}: O estágio final parte de uma imagem base mínima e segura (\texttt{python:3.11-slim}). Ele copia apenas as dependências pré-compiladas do estágio de \textit{builder} e o código-fonte da aplicação. Crucialmente, um \textbf{usuário não-root} (\texttt{appuser}) é criado e utilizado para executar a aplicação, uma prática de segurança fundamental que reduz a superfície de ataque em caso de uma vulnerabilidade.
\end{itemize}

O resultado é uma imagem Docker enxuta, segura e otimizada, contendo apenas o necessário para a execução da aplicação em produção.

\subsubsection{Orquestração em Ambiente de Produção (docker-compose.prod.yml)}

Para a orquestração dos serviços em produção, foi criado o arquivo \texttt{docker-compose.prod.yml}, que define um ambiente estável e resiliente.

\begin{itemize}
    \item \textbf{Servidor de Aplicação Robusto}: Em vez de usar o servidor de desenvolvimento do Uvicorn com \textit{hot-reloading}, o serviço da API é executado com o \textbf{Gunicorn} como um gerenciador de processos, que por sua vez gerencia os workers \texttt{uvicorn.workers.UvicornWorker}. Esta é a configuração padrão da indústria para rodar aplicações FastAPI em produção, garantindo estabilidade e performance.
    
    \item \textbf{Reinicialização Automática}: Todos os serviços críticos (API, worker Celery, banco de dados, Redis, etc.) são configurados com a política \texttt{restart: unless-stopped}. Isso garante que, em caso de falha ou de reinicialização do servidor host, os contêineres sejam reiniciados automaticamente, aumentando a disponibilidade da aplicação.
    
    \item \textbf{Segurança de Rede}: As portas dos serviços de infraestrutura internos, como o PostgreSQL e o Redis, não são expostas ao host. A comunicação entre os contêineres ocorre de forma segura através de uma rede Docker interna e customizada (\texttt{app-network}), minimizando a exposição de serviços sensíveis.
    
    \item \textbf{Configuração Centralizada}: Todos os serviços carregam suas configurações a partir de um único arquivo \texttt{.env}, garantindo a consistência e facilitando o gerenciamento das variáveis de ambiente em produção.
\end{itemize}

Esta configuração de implantação fornece um ambiente de produção completo, seguro e resiliente, pronto para ser executado em qualquer máquina que possua Docker e Docker Compose.
